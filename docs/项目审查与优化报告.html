1.1 项目定性

算法层是真资产，工程层是欠债区。 算法部分（拍摄形式前置校验、OOD 分布外拒识、Grad-CAM++ 病灶定位、色温异常通道） 四者互不重复、各有实测标定依据，是与同赛道竞品形成分野的差异化内核，本次未改动其算法逻辑与标定阈值。 工程部分（并发模型、安全边界、契约一致性、依赖锁定、仓库卫生）问题密集， 但绝大多数属于低风险可渐进修复的欠债。

1.2 最关键的三个发现

发现一 · 虚拟环境已损坏，项目根本无法启动。 .venv/pyvenv.cfg 中的基础解释器路径指向一个已不存在的用户目录， 导致 .venv\Scripts\python.exe 直接报 did not find executable， run.bat 完全无法运行。项目的 4.57 GB 依赖包体完好，仅此一行配置失效。 已修复（备份 pyvenv.cfg.bak），修复后 torch 2.13.0+cu126 / CUDA 可用 / ultralytics 8.4.137 全部正常。

发现二 · 存在已实测复现的同源存储型 XSS。 原实现把用户可控的文件后缀直接拼进落盘文件名，而 /uploads 是静态挂载。 审查中实际上传了一个 HTML 文件，GET /uploads/<uuid>.html 返回 200 + Content-Type: text/html，浏览器会把它当同源页面执行， 脚本可读取本页 DOM 与 localStorage。已通过 「体积上限 + 扩展名白名单 + 真实魔数校验」三道检查封堵（含改扩展名绕过）。

发现三 · 核心差异化能力 OOD 拒识的阈值，是按重训前的旧模型标定的。 项目开发文档中整套标定数据（合规图 0.43 / 枫叶 0.33 / 合成椭圆 0.26 / 葡萄叶 0.19） 均来自 2026-09-01 的首轮模型；而 2026-09-15 用 60,343 张数据重训了 v2 模型， 特征空间随之改变——连项目自带的合规示例图都从约 0.43 变为 0.3691。 阈值 0.25/0.32 未随之复核。更直接的影响是： 合成图形已无法触发拒识区，现场演示「拒识」环节必须改用真实非支持作物叶片照片。 详见第七节。

1.3 一个必须说明的过程事实

本项目的代码从未纳入版本控制（无 .git）。这意味着审查开始前 无法先做一次基线快照再动手。为弥补，审查阶段记录了全部关键文件的 SHA-256 指纹， 且六份详细审查报告（.workbuddy/review/）逐条给出了 文件:行号 级的证据，修改前后的差异可据此核对。 首个提交 d5b8053 已建立基线，此后的任何改动都可回滚。

四、缺陷清单与修复状态

4.1 正确性缺陷（P0）

缺陷证据与后果处理
兜底模型类型错误 config.py 的 FALLBACK_MODEL="yolo11n.pt" 是检测模型， 而 detector.load() 无条件访问分类头独有的 .conv。 实测对照：分类权重末层为 Classify 且 hasattr(.conv)=True； 检测权重末层为 Detect、hasattr(.conv)=False， 复现出 AttributeError: 'Detect' object has no attribute 'conv'。 后果：models/best.pt 缺失时首个请求即崩，且故障恰好推迟到演示现场。 已修 改指向同目录的分类兜底权重 yolo11n-cls.pt， 并加结构断言与明确报错
事件循环被阻塞 main.py 的 async def predict 函数体内全程同步阻塞 （落盘、OpenCV、YOLO 推理、requests 调大模型）。 后果：单次请求进行中，/health 与静态文件全部无响应， 大模型最坏超时 30 秒内整个服务假死。 已修 改为 def 交由线程池； 推理临界区加锁；大模型调用置于锁外
共享可变状态竞态 detector._penultimate_features 由 forward hook 写入实例属性， 而 detector 是模块级单例；gradcam 还会临时切换 requires_grad。原靠"事件循环被阻塞"意外串行化，一旦真并发即互相覆写。 已修 特征改为每次调用注册局部 hook、用完即移除
热力图定位几何不一致 识别路径走 ultralytics 的「短边缩放 + 中心裁剪」，可视化路径走「直接拉伸整图」 再把 CAM 拉回整图。两条路径看到的内容范围不同，非方形图上病灶位置会画错。 项目自带示例图恰好是 256×256 正方形，两条路径等价，所以一直未暴露。 已修 可视化改为同几何，CAM 映射回中心方形区域
预热失败阻断启动 启动钩子中的模型预热会清理一个临时文件；该清理一旦抛出异常 （实测在某些环境下抛基类异常，except OSError 抓不住）， 直接导致 Application startup failed. Exiting. —— 服务完全起不来。 纯辅助动作不应具备拖垮启动的能力。 已修 预热全链路改为不可阻断启动
上传目录缺失即无法启动 StaticFiles 在 import 期挂载时即检查目录存在性， 而建目录动作在 startup 钩子里（更晚）。后果：uploads/ 一旦缺失 （被清理、或全新克隆的仓库里没有该目录），服务连启动都做不到。 已修 建目录提前到挂载之前
冒烟测试必然崩溃 scripts/smoke_test.py 直接对 detect() 的返回值做迭代， 但该函数返回四元组 (detections, ood, is_ood, is_warning)， 迭代后取 d.name 必然抛 AttributeError。该脚本一直是坏的。 已修 正确解包，并补模型信息与来源输出

4.2 诚实性与契约缺陷（P0）

缺陷证据与后果处理
处方来源不透明 原实现在无密钥或调用失败时静默回落模板，外部无法分辨。 而对外材料一直以「大模型个性化处方」为核心卖点—— 评审若查证，即构成"声称大模型、实跑模板"的事实性风险。 iCAN 对本赛道材料不实是直接取消资格。 已修 响应体新增 prescription_source， 界面如实标注「内置模板兜底」
阈值双份真源 前端把「拒识阈值 0.25 / ≥0.32 为正常」硬编码在自己代码里， 与后端常量各自维护、无同步机制。而阈值历史上调整过两次 （0.40 → 0.35/0.40 → 0.25/0.32），且这段文案显示在结果区正文里， 一旦漂移就是答辩现场「文案说的数和实际判的数对不上」。 已修 新增 GET /api/v1/meta 与响应体回传， 前端只读不写
业务常量三处重复 支持作物清单同时存在于 detector.py（英文表）、 main.py（拒识提示的硬编码中文长串）、 frontend/index.html（中文列表）。 已修 收敛到 constants.py 单点真相

4.3 静默失败（P1）

  • gradcam.py 的 except Exception: return None 无任何日志 → 系统性失败（层不匹配、显存不足）在演示中表现为「功能悄悄没了」却无从定位。已补日志。
  • prescriber.py 的 except Exception 掩盖配置缺失， 使系统"看起来有大模型处方"实际是模板（即上面 4.2 第一条的技术成因）。已补日志并区分预期异常。
  • gradcam.py 中有一处「先算 Otsu 得到着色掩膜、随后立即被覆盖」的无效计算， 属死代码，已移除。

4.4 编码质量缺陷（P1/P2）

问题证据处理
硬编码层索引 gradcam.py 用 _TARGET_LAYER=9 / _HEAD_LAYER=10， detector.py 用 list(children())[-1] —— 同一 backbone 两套不一致的寻址约定。换模型或升级 ultralytics 会静默指向错误的层： 不报错，但热力图语义全错。 已修 新增 model_arch.resolve_backbone() 按类型内省， 两侧统一调用
前端内存泄漏 app.js 每次上传都 createObjectURL， 全仓无 revokeObjectURL。连续换图会累积 blob， 低配演示机可能触发 GC 抖动。 已修 持有引用并在赋值前释放
无加载态 / 无并发守卫 原先加载态只有一行纯文本，fetch 无取消、无请求序号。 演示时连点两次会产生两个并发请求，陈旧响应可能覆盖新结果 （而当时后端还是同步阻塞的）。 已修 AbortController + 请求序号 + spinner + 超时文案 + 重试按钮
硬编码颜色 styles.css 12 处、app.js 9 处非例外色值。 已修 全量收敛为语义 token
emoji 作功能图标 欢迎弹窗用 emoji 作徽标，而项目已有品牌 SVG 资源却零引用； 上传按钮用纯文本 + 作图，三端字体渲染不一致。 已修 改用 logo_icon.svg 与描边 SVG 图标
上传参数无意义 model.predict(..., conf=0.25) 对分类任务无过滤作用 （分类头始终输出全部类别概率），且恰等于库默认值，属冗余误导。 已移除 行为完全一致
render 状态清理不对称 成功分支迟到清理处方区；detections.forEach 无兜底， 依赖 schema 默认值这一隐式契约，后端一旦改为 Optional 即白屏。 已修 统一重置 + Array.isArray 兜底

已复核确认「不是问题」的疑点（避免误改引入回归）

疑点复核结论
可视化未做 ImageNet 归一化 不需要。该模型内置 Normalize(mean=0,std=1)，其 scale=1/255 与手工预处理一致。
分类任务传 conf=0.25 有害 无实际影响。分类头输出全部类别概率、不做 conf 过滤，且该值与库默认值相同。
top5 长度可能不足 3 不成立。实测 len(top5)==5，取 Top3 正确。
手机照片 EXIF 旋转导致识别错误 不成立。cv2.imread 不应用 EXIF 方向，推理与热力图共用同一未旋转原图，几何自洽。
前端 XSS 注入面 改造前已闭合：所有用户可见插值点要么经转义、要么用 textContent。 本次进一步改为 createElement 组装，消除字符串拼 HTML 的未来风险。

五、安全隐患排查与封堵

隐患证据与影响处理
P0 存储型 XSS 用户可控后缀直接拼进落盘文件名，/uploads 静态挂载。 已实测复现：上传 poc.html 后 GET /uploads/<uuid>.html 返回 200 + text/html，浏览器按页面执行。 已封堵 魔数校验（拦住改扩展名绕过）
P0 无上传边界 无体积上限、无类型白名单。超大图会让推理显著退化（实测 12MP 照片的 热力图耗时是示例图的十余倍），并抬升内存占用。 已封堵 12MB 上限 + 白名单 + 长边收敛到 1600px
P1 上传永不清理 实测 259 个文件 / 11.5MB 只增不删。用户上传的作物照片属用户数据， 长期留存在本地既无必要也不妥当。 已封堵 惰性回收（保留 24 小时，带超频保护）
P1 CORS 全开 allow_origins=["*"] + allow_methods=["*"] + allow_headers=["*"]，等价于允许任意站点从浏览器读取本机推理服务结果。 已收敛 仅保留本机演示所需来源
P1 进度面板暴露密钥 serve_panel.bat 用 http.server 托管整个项目根目录， 会把 .env 暴露为可 HTTP 读取；且该面板功能早已废弃 （训练结束，其数据源为空数组）。 注意：一旦按建议配置了真实 .env，此风险即被激活。 已删除 该脚本与面板相关文件（已备份）
P1 演示环境联网不可控 ultralytics 在找不到权重、做 AMP 检查或遥测时会尝试联网； 而比赛现场网络不可控。原先兜底权重名还会触发从 GitHub 下载。 已封堵 离线优先环境变量 + 模型一律本地加载
P1 占位符密钥导致长超时 若把 .env.example 误复制为 .env， 程序会认为"已配置密钥"而真的发起请求，每次等满 30 秒超时—— 现场演示的致命事故。 已封堵 占位符与过短密钥识别为未配置； 超时拆分为连接 3.5s / 读取 12s
P2 无鉴权 / 无限流 /predict 无任何访问控制。本机演示形态下风险可接受 （绑定 127.0.0.1）；但若改为公网可访问，必须先做鉴权与限流。 待定 取决于最终演示形态（见第九节）

6.2 三处会直接导致失败的问题

  1. ultralytics 未锁版本（最高风险）。原写 ultralytics>=8.2， 而项目日志明确记录 8.4.153 的 predict 会对模型做 deepcopy， 与 forward hook 冲突，报 cannot pickle '_thread.lock' object 导致推理完全不可用。 这意味着任何一次 setup.bat 都可能装上一个会崩的版本。 已锁定为实测验证过的 8.4.137，并附原因注释。
  2. requirements.txt 缺 torch/torchvision。 单独执行 pip install -r requirements.txt 会装出一个没有 torch 的环境； 而直接让 pip 通过 ultralytics 传递依赖安装，会装成 CPU 版，GPU 推理失效。 已明确「必须先装 PyTorch、再装其余依赖」的顺序，并在 setup.bat 中固化。
  3. setup.bat 与实际 CUDA 不符。原脚本装 cu121，而实际环境为 cu126。 已对齐并改为「CUDA 12.6 / CPU」二选一，且安装后自动跑一次导入自检。

6.3 已落地的配置改进

  • .env 解析：由手写解析（不处理引号 / export 前缀 / 行尾注释 / BOM） 改用已安装却未被使用的 python-dotenv。
  • 消除 import 副作用：原 config.py 在 import 时即创建三个目录 （含体积很大的 data/），使任何 import app.config 都产生磁盘副作用， 测试与工具链无法干净隔离。已改为显式调用。
  • 依赖分层：新增 requirements-train.txt， 把绘图与大数据处理库从推理运行时中分离，部署镜像可更精简。
  • 启动脚本加固：run.bat 增加虚拟环境 / 模型权重 / 端口占用三项前置检查， 缺失兜底权重时明确警告「识别结果无实际意义，请勿用于演示」；不写字节码；离线环境变量。
  • .gitignore 重设计：原设计直接忽略 runs/，但该目录下的 训练结果 csv、混淆矩阵与训练曲线是原创性举证的硬证据。 已改为「忽略中间图像与权重复本，保留训练记录」，实现 「代码进版本控制、大体积数据不进、但参赛证据必须进」。

6.4 两处「看起来配了、其实没生效」的假象（比不配更危险）

假象一 · 我本人在改造中引入的一个缺陷：CUDA 安装分支会静默退化成 CPU 版。 我给 setup.bat 写的是 --index-url https://mirrors.aliyun.com/pytorch-wheels/cu126/。 但该地址是扁平的 wheel 目录，不是 PEP503 索引 —— pip 会去请求 .../cu126/torch/ 并拿到 HTTP 404，随后回落到 PyPI 上 不带 CUDA 版本号的 torch 包。 也就是说：脚本执行"成功"，装到的却是 CPU 版。 已修正为 -f（find-links）指向 wheel 目录 + 版本号显式带 +cu126， 并在安装后断言 torch.cuda.is_available() —— 仅凭 pip 返回成功无法判断装到的是哪个版本，必须断言。

假象二 · 两个环境变量设了但无效。 经实测核实，ultralytics 8.4.137 源码中 真正生效的离线开关只有 YOLO_OFFLINE； 原先同时设置的 ULTRALYTICS_OFFLINE 在该版本中零引用、完全无效。 这类"看起来已封堵、实际没生效"的开关会让人误以为现场断网安全，风险高于不设。 已从 config.py 与 run.bat 中移除。 同理，.env.example 里的 LLM_ENABLED 原先并未被代码读取 （是个空开关），现已让配置层真正读取它。 若将来升级 ultralytics，必须重新核实生效的开关名。

七、回归测试的沉默失败（重要）

项目唯一的端到端回归脚本 scripts/verify_pipeline.py， 在审查时实测为 4/5 失败。这不只是"少通过一项"，而是暴露了一个更深的问题：

失效链条

  1. 脚本用「纯白底 + 绿色椭圆」合成图作为拒识区夹具，期望其 OOD 分数约 0.24（< 0.25）。
  2. 该期望值是 2026-09-01 按首轮模型实测标定的。
  3. 2026-09-15 用 60,343 张数据重训了 v2 模型，特征空间改变，整条 OOD 分布下移约 0.05–0.06。
  4. 同一张合成图在 v2 下变为约 0.30，落进警告区，于是断言失败。
  5. 但脚本自重训后从未重跑，因此这个失败一直被隐藏。

连带影响：开发文档与代码注释中记录的整套 OOD 标定值 （合规图 0.43 / 枫叶 0.33 / 合成椭圆 0.26 / 葡萄叶 0.19）全部来自重训前的模型， 已不可直接引用。

9.3 针对对手优势的三条反制要点

  1. 「9 个模型」是把专家门槛转嫁给用户，不是更专业。 按作物拆模型隐含一个前提：用户得先知道这是什么作物。可真实场景里， 农户拿到的就是一片病叶，他连病害都判不准，更判不准该选哪个模型—— 选错模型 = 诊断必错。禾目单模型同时判作物与病害，用户零门槛。
  2. 覆盖广度是工程量，可解释与拒识是方法论。 本赛道创新性 35 + 原创性 20 + 技术方案 20 = 75 分，考的是突破而非类目数量。 把作物从 14 种堆到 23 种是数据工程量的增加； 而「感知自己不知道」是所有图像 AI 落地的共性难题，更难、更本质、更可迁移—— 做完主粮数据，这条技术栈能直接迁移过去；反之只堆模型不做拒识， 用户拿到的仍是一个会自信答错的系统。
  3. 现场可验证的对比动作。 建议请对手演示一次"上传一张不在训练集里的图片"会发生什么——大概率给出高置信度的错误答案； 而禾目会明确拒识。农业诊断要对症下药，错误诊断的代价是买错药、药害、农残。 「宁可说不知道，也不乱开方」不是功能少，是职业底线，也正对应国家「化肥农药减量增效」的方向。

9.4 是否赛前补中国主粮：明确结论——不补

  1. 时间与数据不可得。区域赛窗口仅有约一个月。中国主粮的公开数据集多为 检测框标注而非分类标注，需重做清洗、类别归一化、中文映射、阈值重标定与全链路回归， 这是一个以周计的完整链路。
  2. "做一半"的减分风险高于"不做"。只加一两种且精度未标定， 会两头不讨好——既没覆盖全，又破坏了当前"14 类全覆盖、单模型自洽"的干净叙事。
  3. 正确解法是把它写成路线图，把短板转化为价值观。 「我们宁愿只覆盖 14 种并保证可信，也不愿覆盖 23 种却让农民拿到错误处方。」 再给出可迁移的技术路线，短板就变成"有原则地先做可信、再做全面"。

9.5 答辩必备：诚实口径

关于大模型处方。当前 .env 未配置，处方走的是内置模板。 这是工程上的容错设计（有密钥走通义千问，无密钥走模板）， 且界面已如实标注来源。绝不能在演示时把模板处方说成大模型生成—— 这是被追问即穿帮的事实性风险。答辩前建议二选一：配好密钥让大模型真跑， 或在演示时明确说明"当前展示为模板兜底，接入大模型后为个性化处方"。

关于 99.7% 的准确率。必须明确区分：这是实验室分布下的 top1 准确率。 自测显示田间实景的 OOD 分数仅 0.17–0.20，会被拒识。 正确表述是：「99.7% 说明模型在给定分布下确实学到了判别特征， 而 OOD 拒识保证这个数字不会被用在分布外样本上骗人」。

关于模型坍缩的复核。开发日志曾记录早期模型出现"坍缩" （32 张图中 68.8% 被判为同一类）。本次已用混淆矩阵复核： 38×38 归一化混淆矩阵为一条干净的对角线，各类可分，坍缩问题已解决。 这条"曾坍缩 → 定位为数据不平衡 → 重训 → 混淆矩阵逐类复核达标"的闭环， 比"一直很好"更有说服力，建议主动讲。

关于单叶 + 纯色背景。这是当前的真实局限，应正面承认而非回避。 转化为技术亮点的逻辑是：所有图像分类模型的能力都由训练分布决定，这是共性而非本项目 bug； 禾目没有硬给一个错误答案，而是前置拦截 + 主动拒识—— 「拍不对，我先拦下来，而不是给你一个假结果」。
