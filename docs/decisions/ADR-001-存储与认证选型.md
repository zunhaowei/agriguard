# ADR-001: 功能扩展的存储与认证选型

## Status

Accepted (2026-09-21)

## Background

用户要求为前端新增「登录界面、病例库、历史记录、语音朗读」，其中历史记录明确提到
"对接已有的远端数据库"。但经核查存在两个事实问题：

1. **项目里根本没有任何数据库**（无 SQLAlchemy / SQLite / MySQL 痕迹），"已有的远端数据库"不存在。
2. **演示形态是本机离线**（服务绑定 `127.0.0.1`）。若历史记录依赖远端云库，
   现场断网时该功能失效 —— 而巡展评分中"现场演示效果"是单项最高权重（50 分）。

另需说明的概念混淆（已向用户澄清）：**Gitee 是代码仓库，不是数据库**。
前者存源代码与版本历史（提交后固定），后者存运行时数据（用户、诊断记录，持续增长）。
用户已知晓并确认改用本地方案。

同时，本项目依赖纪律严格（`ultralytics` 已锁死 8.4.137，多版本曾导致推理完全不可用），
每新增一个第三方库都会抬高"换机器复现"的风险。

## Decision

本组决策一并锁定：

| # | 决策 | 选择 |
|---|---|---|
| D1 | 数据库 | **本地 SQLite**，使用 Python stdlib 的 `sqlite3` |
| D2 | 数据访问层 | **不引入 ORM**；3 张表规模，手写薄仓储层即可 |
| D3 | 密码存储 | stdlib `hashlib.pbkdf2_hmac`（SHA-256，20 万轮 + 每用户 16 字节随机 salt） |
| D4 | 会话 | 数据库会话令牌（`secrets.token_urlsafe(32)`，7 天过期，登出即删） |
| D5 | 历史缩略图 | 存 **SQLite BLOB**，不存文件 |
| D6 | `/predict` 认证 | **可选**（带 token 才入库），保持向后兼容 |
| D7 | 前端形态 | 保持**原生多页面**（无构建链），不引入 Vue/React |

## Consequences

### 正面

- **零新增 pip 依赖**：本次功能全部用 stdlib 完成，依赖面不扩大，
  "换机器复现"的风险不增加。
- **离线可用**：除大模型处方外，全链路断网可跑。演示零风险。
- **可备份**：整个数据库就是 `data/agriguard.db` 一个文件，拷贝即备份。
- **既有回归不受影响**：`/predict` 签名与响应体不变，14 项测试无需改动（D6 的直接收益）。
- **可撤销会话**：登出即从 `sessions` 表删除，比无状态 JWT 更适合演示场景（能演示"登出后失效"）。

### 负面 / 需接受的代价

- **无多端共享**：换台电脑看不到历史。若后续要，需自行加同步（已列入 OPEN-DECISIONS）。
- **手写 `sqlite3`** 比 ORM 啰嗦，且需自行处理连接与事务。
  缓解：表结构极简，封装为独立 `db.py` 模块，路由层不直接写 SQL。
- **`data/` 已被 `.gitignore` 排除**，数据库不会进版本控制。
  这是刻意的：运行数据不应入库，且避免参赛材料里混入用户数据。
- **单文件数据库的并发能力有限**。当前为单机单进程，`uvicorn` 单 worker，可接受；
  若将来多 worker，需改为 WAL 模式或换库（记入风险）。

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 远端云数据库（如 Supabase / 腾讯云） | 与"本机离线演示"直接冲突；断网功能失效，演示风险不可接受 |
| 本地为主 + 远端同步 | 最稳妥但工作量最大，赛前时间预算不允许；已列入 OPEN-DECISIONS 待评估 |
| SQLAlchemy ORM | 为 3 张表引入一个重量级依赖，与项目依赖纪律不符 |
| 无状态 JWT（PyJWT / python-jose） | 需新增依赖；且无法演示"登出即失效" |
| 缩略图存文件 | `uploads/` 有 24 小时惰性回收，历史记录里的图会**过一天变空白** |
| 强制登录才能诊断 | 抬高使用门槛，且会破坏既有 14 项回归测试 |

## 后续跟踪

- 若演示环境网络稳定且用户提出多端需求 → 重新评估 D1（见 `OPEN-DECISIONS.md`）。
- 若历史记录数超过约 1000 条导致列表变慢 → 评估分页索引与 VACUUM。
- 若将来部署为多 worker → 必须重新评估 SQLite 并发（改 WAL 或换库）。
